# Compilation-database example

This benign two-translation-unit capacity contract uses the same verifier and synthesizer as other programs. `src/operation.c` uses the recorded C99/GCC recipe, relative include path, macro and response file. The verification harness uses explicit C11 flags. This relocatable example interprets database directory `.` relative to the database file; a database generated by a real build normally supplies an absolute working directory.

From the repository root, with the configured CBMC 6.11.0 toolchain:

```sh
python -m tools.verification tests/verification_cases/compilation_database/task.json \
  --synthesize tests/verification_cases/compilation_database/sketch.json \
  --toolchain /path/to/toolchain.json --output build/verification/build-example
```

Expected synthesis: decision table `[0, 1]` for predicate `count > 4`, where 0 means PASS and 1 means return -1. The actual caller checks the returned result. The accepted policy file under the run directory can be supplied to `--policies` for an independent run. The overall status remains UNKNOWN and exit code 2 because lifecycle induction and runtime correspondence are pending; `SOLVED_FOR_HARNESS` identifies the completed synthesis obligations.

Inspect `preprocessed/build.json` and `dependencies.json` under a candidate's verification directory for the resolved build recipe, response-file hash, native compiler identity and ABI checks. The example creates no `operation.o` in its source directory.
