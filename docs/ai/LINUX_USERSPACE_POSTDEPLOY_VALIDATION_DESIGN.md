# Linux 用户态补丁部署后通用功能验证：实现方案

日期：2026-11-12。状态：待实现的工程设计。

本方案以已接通的 Frida 用户态后端、原生 eBPF VM、`tools/verification/` 的 CBMC 工具链为基础。目标是让新应用通过提供构建信息、请求边界、正常输入约束和结果契约，复用同一套补丁部署后验证代码。

交付结果分三部分：影响范围证据、配对功能测试结果、部署后路径与可用性变化报告。部署后验证针对已安装的补丁身份执行；模型检查可以在控制机上运行，功能采集在 Linux 目标进程中执行。

## 1. 与现有实现的连接

| 已有能力 | 复用方式 | 本方案新增部分 |
|---|---|---|
| `runtime/frida/agent.js` 的观察和入口替换 | 继续负责执行策略，保留 PASS/BLOCK | 请求关联、安装回执、执行结果事件、共享挂点分派 |
| `runtime/frida/bridge.c` 和 `runtime/vm.c` | 继续执行实际规则字节码 | 批量遥测通道；VM 指令集保持独立演进 |
| `tools/verification/engine.py` | 复用编译、模型检查、调用者契约和证据绑定 | 原/补丁程序的配对模型、影响区域自动分类 |
| `tools/verification/runtime.py` | 复用字节码和运行时身份核对 | 关联“验证的规则”与“进程中加载的规则” |
| `tools/application_binding.py` | 复用源、构建、ELF 和产物哈希 | 活进程、模块装载地址、补丁版本回执 |
| 既有 Nginx 模型实验 | 保留为算法回归用例 | 真实进程、真实接口、配置化 Oracle、统一报告 |

当前 10 项 Frida 集成测试验证了挂载机制。本方案中的请求级采集、配对执行、自动影响分类和覆盖统计都是新模块。

## 2. 统一工作流

```text
应用说明 + 正常输入/状态契约 + 补丁清单 + 构建信息
                           │
                           ▼
              确认已安装补丁及目标二进制身份
                           │
                           ▼
              差分符号分析 → 影响范围与输入分区
                           │
                 ┌─────────┴─────────┐
                 ▼                   ▼
       可重置副本中的配对测试     已部署进程中的被动采集
       功能输入变异 + Monitor    路径/结果/延迟/采集质量
                 │                   │
                 └─────────┬─────────┘
                           ▼
            功能回归、预期变化、统计异常、证据缺口
```

第一条路线回答“同样的正常操作，补丁部署后是否仍得到契约允许的结果”。第二条路线回答“真实使用中，原来正常可达的功能是否明显减少或消失”。两条路线共享接口标识、输入分区、事件格式和补丁身份。

主目标平台是 Linux x86-64 本地原生进程。运行时采集以无需重新编译的 Frida 为默认后端；有源码和构建参数时启用 CBMC 差分分析。只有二进制时，运行时验证照常工作，影响范围采用保守的接口/函数范围，并单独记录静态分析证据。

## 3. 通用引擎需要哪些应用输入

### 3.1 自动获取与显式提供的分界

| 信息 | 来源 |
|---|---|
| 进程、装载模块、ELF build-id、文件 SHA-256、挂点位置、已加载规则哈希 | 系统自动采集 |
| 源码调用关系、受影响分支、可观察字段类型、部分输入分区 | 编译器和符号分析 |
| 请求/操作从哪里开始、在哪里结束 | 应用 profile 的显式绑定 |
| 异步操作如何提交、恢复、完成 | profile 的显式交接点 |
| 什么是正常输入、允许的状态序列 | 接口 schema、功能测试和状态契约 |
| 返回值、响应、输出参数、持久化效果如何判定正确 | 应用契约和参考运行 |
| 哪些差异被允许 | 部署前固定的比较规则 |

通用性落实为“同一个采集器、分析器、输入调度器、比较器和统计器读取不同 profile”。业务规则放在 profile/适配器中，核心代码不按软件名称或漏洞编号分支。

### 3.2 三份输入文件

1. `deployment.json`：目标程序与补丁身份。引用实际 Frida manifest、动作目录、字节码、VM/agent 版本及各自哈希。
2. `application.json`：接口、请求边界、显式观察点、异步交接、输入编码、状态重置方式、结果契约。
3. `validation-plan.json`：输入域、分区、必须出现的检查点、采样率、执行预算、统计阈值、对比组定义。

应用契约支持内置原语：整数/枚举返回、errno、输出字段初始化与取值、字节串比较、JSON 字段比较、HTTP 状态与指定响应字段、显式资源获得/释放事件、业务效果摘要。复杂业务由一个版本固定的 adapter 实现。

资源状态只从配置的事件更新。例如文件描述符平衡需要显式绑定获得和释放事件；用户态 malloc/free 也需要相应绑定。缺少事件时报告该项证据缺失，不由地址或函数名推断生命周期。

## 4. 部署身份与采集版本

部署回执包含：

- Linux PID、PID namespace 标识、`/proc/<pid>/stat` 的 starttime，防止 PID 重用。
- 每个相关 ELF 的 build-id、文件哈希、实际装载区间和 PT_LOAD 映射。
- 每个挂点的模块身份、原始函数入口、函数原型、安装前字节摘要、安装后跳转摘要。
- 规则、动作目录、观察配置、VM、agent、应用 profile 和 Oracle 的哈希。
- `deployment_epoch` 和测量配置版本；采样率或检查点变化也产生新的测量版本。

模块地址按 ELF load bias 映射到相对于模块虚拟地址基准的偏移；不直接用“地址减第一个 maps 行”代替 ELF 映射。安装后函数序言已经被 Frida 改写，因此文件原始哈希和内存跳转状态分别记录。

一个版本的有效采集窗口从全部必需 worker 完成挂载确认、应用 profile 的预热条件成立之后开始。新增 worker、exec 或模块重载触发重新绑定；未确认的 worker 在部署覆盖率中单列。验证器不会为了取得基线而临时卸载线上补丁。

## 5. 差分符号分析：自动生成影响范围

### 5.1 验证入口与观察终点

从实际 guard 的绑定函数出发，复用编译器调用图向调用者查找，直到碰到 profile 指定的操作入口。一个 guard 可能对应多个入口，全部形成独立验证任务。终点采用该操作的完成/失败契约，包含必要的调用者续体。

入口输入状态由正常接口约束和状态契约构造。源语言分析的首版范围为已支持的顺序 C harness；跨请求状态通过显式操作序列检查。异步/并发行为有单独的执行模型和动态证据，不能由顺序 harness 推得。

### 5.2 原程序与补丁程序的配对模型

新增 `tools/postdeploy/product.py`，在类型化 GOTO IR 上构造：

```text
共享的正常逻辑输入 x、初始状态 s、外部环境事件约束 E
                 │
          ┌──────┴──────┐
          ▼             ▼
  原程序 P0(x,s0)   补丁程序 P1(x,s1)
          │             │
          └──────┬──────┘
                 ▼
       比较可观察结果 O0 与 O1
```

两个版本的函数、全局状态和堆对象使用独立命名空间；由同一个有界类型化初始对象图克隆得到，保留别名、偏移、空指针与初始化状态。输入只读数据可以共享逻辑值，应用可写内存不共享实例。实现前复用现有初始化与指针编码资格检查。

参考版可以选择相同二进制/源码的无策略版本，或已修复的参考版本，选择结果写入计划。源码级配对与二进制上的实际行为分别取得证据。

外部文件、时钟、随机源等通过固定模型或按逻辑操作标识关联的事件记录提供给两个版本。若分支改变导致外部调用序列不同，就记录为效果差异；不能简单让两边各自取“下一次随机值”后假定环境相同。

首版保留真实函数体和调用者，按显式环境摘要处理外部边界。此前模型实验使用的“共享任意后续结果”仍可用于模型回归，但不代替真实应用的后续执行。

### 5.3 差异判定

profile 定义可观察结果：

```text
O = (返回/响应结果, 指定 errno, 输出字段, 持久化效果摘要,
     必须完成的协议事件, 显式资源契约)
```

内存比较只包含有定义的契约字段；跨进程指针按逻辑对象身份比较，不比较地址数值、padding 或未初始化字节。时间戳等字段的归一化规则在运行前固定并记录版本。

对于正常域 Ω，分别提出两个查询：

```text
新增无效执行：Ω ∧ Defined(P0) ∧ ¬Defined(P1)
功能差异：    Ω ∧ Defined(P0) ∧ Defined(P1) ∧ ¬EqContract(O0, O1)
```

`Defined` 由现有运行检查、初始化检查和调用者契约构成。正常输入域也需要可达性检查；一个被假设排空的域不生成保留结论。计划允许的功能变化单独列入 `allowed_changes`，默认正常功能结果保持一致。

实现时先生成参考侧的定义性条件，作为上述差分查询的前置条件；补丁侧的检查仍是待验证断言。完整性、展开界限和环境假设单独保存，不能将补丁侧失败改写成假设而过滤掉。函数返回、错误返回和已建模的非正常结束均需要确定的比较出口；遇到尚未支持的退出方式，当前分区保持 UNRESOLVED。

### 5.4 自动分区和求解算法

初始谓词来自 guard 比较条件、观察状态是否存在、关联调用者分支、接口 schema 中的枚举与区间。使用布尔向量或区间构造分区 C；默认最多 8 个谓词和 256 个分区，预算可配置。

```text
worklist = 初始输入分区
for C in worklist:
    求解 Ω ∧ C
    若完整结果为不可达：标记 UNREACHABLE
    否则求解 C 内的“新增无效执行”与“功能差异”
    两者均完整 UNSAT：标记 PRESERVED_FOR_MODEL
    任一 SAT：保存见证摘要，标记 MAY_CHANGE
    未完成：标记 UNRESOLVED
    对 MAY_CHANGE/UNRESOLVED，按首次可观察分歧相关谓词继续拆分，直到预算用尽
```

影响上界 `I+` 是所有 MAY_CHANGE 和 UNRESOLVED 分区的并集。已找到差异的样本构成见证集合，不把整个 SAT 分区都视为必然改变。拆分候选由分歧处的数据/控制依赖提供，无法缩小时保留较大的分区。

输出 `impact.json`：入口、谓词、分区约束、可达性、影响上界、可能改变的结果字段、调用者续体、需要测量的检查点，以及模型边界和依赖哈希。

谓词相同的输入称为“测试分区”。只有完成了所声明结果关系的验证，才对该分区声称行为保持；一个代表样本通过不表示整个分区已证明等价。

只有二进制或源码模型未闭合时，`I+` 退化为声明的相关接口域。这个范围仍可驱动动态测试，但保持证据类型为运行测试。

## 6. 请求关联：支持同步与异步用户态程序

### 6.1 同步调用

profile 显式指定操作 begin/end。begin 生成 measurement token，压入当前线程的测量栈；end 记录结果并结束 token。递归与嵌套调用保留 parent token。相关 guard 事件从测量上下文取得 token。

### 6.2 事件循环与跨线程执行

Nginx 同一 worker 会交错处理多个请求，因此使用显式 request handle 与测量代次，而非线程号。profile 绑定：

```text
BEGIN(handle)             创建 measurement token
SUSPEND(handle)           当前线程退出该请求执行上下文
RESUME(handle)            当前线程进入该请求执行上下文
TRANSFER(handle, job_id)  关联工作任务
COMPLETE(handle)          结束逻辑请求并清理测量关联
```

上述事件只在配置的程序位置发生。指针复用依赖显式 BEGIN/COMPLETE 区分代次；缺少交接或完成事件时，记录 `context_unresolved`，对应样本不用于完整路径比较。测量映射与补丁观察映射分开存储，测量 token 不补充策略缺失的观察值。

先实现同步 profile，再实现一个 Nginx 版本的请求边界和 worker 交接 profile。其他应用通过相同接口接入。

PHP/Node 等运行时的原生 C/C++ 路径可以使用此采集器；脚本级请求与函数路径要额外提供运行时语义事件。原生解释器路径的覆盖率不直接命名为 PHP/JavaScript 业务代码覆盖率。

## 7. 路径采集后端

### 7.1 L1：语义检查点，默认线上启用

在操作 begin/end、guard、影响范围内关键调用者分支、功能完成事件设置有限检查点。检查点记录 event ID、请求 token、必要的取值类别与结果摘要。

在线采集使用固定检查点表。函数入口/返回可以使用 Interceptor；函数中部检查点需要新增构建绑定的指令地址支持、可用 USDT 或源码插桩。没有指令映射时先采集可用函数检查点，并在报告中写出覆盖层级。

当测量点与现有 policy/observer 位于同一地址时，由统一分派器合并。顺序是显式观察、策略决策、原函数执行或绑定返回、结果事件。避免多个 replacement 相互覆盖；规则返回语义仍只有 PASS/BLOCK。

### 7.2 L2：区域基本块采集，测试副本和抽样请求启用

使用 Frida Stalker 跟踪选定线程，限制到影响范围及调用者相关模块。在代码转换时为实际执行的块入口放入原生 CModule callout。callout 在执行时读取测量 token，并记录原始指令地址对应的 block ID。

计数依据实际执行事件，不能把 Stalker 的代码编译事件当作执行覆盖。请求采样在 begin 时决定；线程持续跟踪时，由当前 token 控制是否记录，避免异步请求之间混入数据。

块 ID 由模块 build-id、模块内地址和采集版本构成。ASLR 不改变 ID。两个应用版本的路径只有经过明确的块/源码映射才比较；无法映射时，改用稳定语义检查点与功能结果。

Frida 自身代码、VM 和测量器代码不计入应用路径。被替换的入口序言和 trampoline 单列为 gate 边界；无法准确映射的重定位区域标记为未测量，而不计算成应用新增或丢失的边。

### 7.3 路径表示

一个已完成的请求产生：

- 精确检查点集合及有界事件序列。
- 区域内基本块/边集合，或抽样覆盖记录。
- 顺序签名，以及循环次数的分桶摘要。
- 实际策略选择、操作结果、耗时和采集完整性标记。

“边集合相同”只表示相应粒度覆盖相同，不表示完整路径或业务效果相同。只跟踪局部区域时，相邻记录构成投影后的检查点关系，不能冒充完整 CFG 的直接边。

测试副本保留可定位的精确事件；线上默认保留聚合计数和有界签名。签名用于聚类，出现异常后用精确事件确认。达到事件预算、丢包、缺少 end 都标记为不完整，不能记作“未执行某条路径”。

### 7.4 原生缓冲与数据格式

新增原生批量缓冲，避免每条基本块事件执行一次 JS `send()`。生产者按线程记录到有界缓冲，消费者按批提取；发布记录使用明确的原子序列和内存顺序。首版不在异步 signal handler 内启用测量点，递归记录设置抑制与计数。

事件的共同字段为：

```text
schema, deployment_epoch, measurement_version,
process_instance, tid, producer_seq, request_token, parent_token,
event_type, probe_id, monotonic_time, payload, loss_epoch
```

跨线程顺序通过显式交接事件构造偏序；单纯时间戳或线程局部序号不提供全局因果关系。进程退出但操作未完成时，监督器补记退出事件；资源耗尽与采集丢失分别统计。

路径只对完整采集的请求作严格缺失判断，同时报告所有已开始请求及不完整比例，防止“失败请求没有结束事件”被筛掉后得到虚假的正常结果。

计划预先设置关联、丢失、截断和 worker 覆盖的质量阈值。窗口不达标时不出具 STABLE 结论；先报告 DATA_GAP，保留仍能独立确认的功能错误。采集质量也按接口与输入分区统计，以发现某类失败请求集中丢失的情况。

## 8. 功能路径 Fuzz 与配对执行

### 8.1 输入来源与调度

使用已有正常功能用例、协议 schema、正常样本和状态机序列构建语料。变异包括枚举选择、合法区间边界、可选字段组合、合法编码、重复次数，以及契约允许的操作顺序。运行器支持 HTTP、CLI 和库调用 adapter。

默认调度预算建议为：40% 影响上界内的可行分区、30% 相邻正常边界、20% 影响范围外的保留区域、10% 历史少见但有效的功能。某分区不可达或没有已知合法样本时重新分配预算，并记录未覆盖原因。

输入生成器接收输入约束与分区，不接受“某目标返回码就是正确”的硬编码判定。Oracle 由独立应用契约和参考结果提供。

每个测试分区维护自己的种子队列。一次合法变异若增加未见检查点、区域边、结果类别或合法状态转换，就保留为种子；发现功能差异则进入重复确认队列。调度器优先补齐影响分区中的缺失检查点，再扩大合法取值组合。基于覆盖的反馈始终受到正常输入/状态契约约束。

### 8.2 两个可重置执行环境

对于逻辑操作 x：

1. 由 fixture 建立两个等价初始状态，记录配置、文件/数据库状态版本与依赖事件。
2. 在参考副本和已加载实际补丁的副本运行同一个 x。
3. 收集检查点、路径、策略选择、结果及效果摘要。
4. Oracle 对两次结果应用同一个正常功能契约和预先声明的归一化规则。
5. 状态型接口比较完整操作序列及最终状态，并在下一组测试前重置。

参考副本与补丁副本的外部写入进入各自 fixture 状态。一次逻辑操作不会对共享业务系统执行两遍。确定性测试使用冻结的时间、依赖响应和随机事件；无法控制的变化记录为不可比较样本，另作重复运行统计。

### 8.3 Monitor 的具体职责

| Monitor | 输入 | 判定 |
|---|---|---|
| 安装一致性 | manifest 与进程回执 | 测到的程序、规则和观察配置是否匹配 |
| 调用一致性 | guard、原函数 body、结果事件 | PASS 是否执行原体；BLOCK 是否跳过原体并返回绑定结果 |
| 功能结果 | 响应/返回/输出字段 | 是否满足契约，与参考的差异是否被允许 |
| 必达事件 | 请求 begin/end、检查点 | 必需阶段是否执行、操作是否完成 |
| 资源与状态 | 显式资源、业务状态事件 | 是否满足声明的配对与状态不变量 |
| 效果范围 | 差分区域、实际差异 | 保留区域出现的功能差异是否构成回归 |
| 采集质量 | 丢失、超时、关联与采样信息 | 哪些路径结论可以使用 |

BLOCK 之后继续跟踪调用者，直到操作的显式完成点。允许的拒绝码不自动表示调用者功能正确；失败回退、清理和完成事件仍由同一个 Monitor 检查。

对于已知正常且不允许改变的用例，只要输出或必要效果改变，就报告功能回归。路径变化而结果契约保持的样本记录为行为变化；是否失败由必须保持的检查点契约决定。

### 8.4 输出与缩减

发现回归后在副本中重复确认，并在保持合法输入约束的前提下缩减用例；保存正常用例、最小相关操作序列、两侧事件、契约差异和版本信息。不能复现的差异归为不稳定样本，进入重复测试队列。

## 9. 部署后覆盖与可用性统计

### 9.1 比较单位

按 `(接口、操作类别、正常输入分区、配置版本、参考构建映射)` 分层。分层字段来自补丁决策之前的请求特征，避免按 PASS 或成功结果筛选后掩盖误拒。

基线来自部署前已有测量、可信参考版本的同类工作负载或配对正常回放。缺少可比较基线时先积累当前窗口，报告 BASELINE_MISSING。不同流量结构采用固定分层权重或直接逐层展示，不用总体覆盖率掩盖单个接口退化。

采样在请求开始时决定，使用固定哈希或随机方案，记录 inclusion probability。BLOCK 请求也进入请求总量；强制多采样的 BLOCK 请求只用于诊断，不能直接加入无权重的总体频率统计。

### 9.2 每个窗口的指标

- 必需功能用例通过率与必达检查点完成率。
- 所有已开始请求的成功、错误、超时、未完成比例。
- 请求级的路径/边出现率；每个请求对一条边最多计一次。
- 基线边的保留情况、新增边、路径签名分布变化。
- BLOCK 比例及其中已知正常类别的比例。
- 延迟分位数、进程退出、明确声明的资源不变量。
- 上下文关联成功率、丢失事件率、路径完整率、实际采样率。

可定义加权基线边保留率：

```text
R = Σ[p0(e) × 1(e 在当前完整样本中出现)] / Σ[p0(e)]
```

R 是扫描指标，同时展示每条边的样本量与变化。路径增多也需要检查：它可能对应新的错误回退或重试。

### 9.3 稀有路径与显著变化

对某一分层和边 e，记录基线 `(x0,n0)` 与当前 `(x1,n1)`，其中 x 是包含该边的完整请求数。使用单侧精确比例比较（如 Fisher 检验）检测下降，并同时要求达到配置的实际下降幅度。

单个窗口内对多条边采用 Holm 校正。持续窗口使用预先确定的显著性预算，例如第 t 个窗口分配 `α/[t(t+1)]`，避免反复检查将偶然波动累计成异常。会话内请求相关时按会话/时间块聚合，使用分块重采样而非独立请求假设。

对于零命中的稀有边，先由基线估计保守出现率下界 pL。独立完整样本下，n 次均未出现的概率是 `(1-pL)^n`。例如 pL=1%，未经多重比较调整的 1% 阈值需要至少 459 个当前样本。样本不足标为 SAMPLE_TOO_SMALL，不把零命中直接记为功能消失。

检测规则可以要求连续多个合格窗口；这是运营稳定性条件，不能替代显著性和采集质量检查。

### 9.4 判定与归因

每条发现保留两个字段：

```text
kind: FUNCTIONAL_REGRESSION | EXPECTED_CHANGE | STATISTICAL_SHIFT | DATA_GAP
evidence: PAIRED_CASE | CONTRACT_EVENT | WINDOW_STATISTIC | MODEL_CHECK
```

已知正常配对用例的契约差异可直接作为功能回归。线上路径频率下降首先是统计变化，再通过受影响接口的正常用例回放、BLOCK 关联和结果变化确认原因。

“正常操作占多数”用于选择基线与异常阈值；一个路径缩小仍可能符合补丁预期，因此覆盖信号与功能结果共同判定。检测器只生成报告或预配置通知，不把告警自动改成策略的第三种动作。

## 10. 挂点和 Monitor 的具体集成

现有 Frida guard 在调用原函数前产生 `decision` 事件，新增：

- `guard_begin`：请求 token、策略身份、输入分区编号。
- `guard_decision`：PASS/BLOCK、实际动作 ID、VM 诊断。
- `guard_result`：原函数或绑定动作执行后的返回值类别、指定 errno、耗时。
- `operation_end`：由 profile 的完成点产生，含业务结果摘要。

将 agent 的逐次消息改为批量传输，但保留现有调试模式。监测读取字段遵守 profile 的类型和边界，原生 helper 与日志代码需要保存 errno，测量不会代替补丁设置目标程序状态。

同一替换回调统一捕获前后状态，并通过 `finally` 维护测量上下文。安装/卸载采用 worker 静止或 drain 协议，避免活跃请求跨版本。采集开关变化与策略变化使用不同 epoch 字段。

## 13. 实施顺序与验收

| 阶段 | 实现与验收 | 产物 |
|---|---|---|
| P1：真实进程测量 | 接入现有 Frida；两个独立正常 fixture 仅换 profile 即可运行；验证 begin/end、策略身份、结果、丢失记录 | 安装回执、事件流、功能结果报告 |
| P2：配对功能验证 | 同一正常语料在可重置副本上执行；发现人为设置的过宽拒绝、输出改变、未完成操作；更换 profile 不改核心 | 配对报告、最小正常回归用例 |
| P3：自动符号影响 | 从源码/实际补丁构造配对模型；自动分区；完整 UNSAT、差异见证、预算耗尽分别输出；更换源码不改验证器 | impact.json、分区与证据 |
| P4：区域覆盖与线上统计 | L2 与简单源码计数 oracle 对照；实际执行次数不受 Stalker 缓存影响；路径丢失、流量变化、丢包、稀有路径四类能区分 | 覆盖报告、统计发现 |
| P5：真实应用接入 | 一版 Nginx 的同步/异步正常操作；明确的 worker/请求完成绑定；正常请求配对测试与测量开销评估 | Nginx profile、部署后验证回执 |

工程上先交付 P1/P2 的通用闭环，供 P3 的影响范围直接驱动；最终工作流仍按“符号影响分析 → 分区测试 → Monitor → 部署统计”运行。

必测回归包括：ASLR、PID/地址复用、递归调用、异步交错、跨线程交接、worker 重启、部署版本切换、延迟完成、事件截断、基线缺失、非确定输出、重复采样和采集开销。

采集开销用相同的正常负载分别运行“无测量、L1、指定比例 L2”三组，记录吞吐与延迟分位数。开销预算由应用 SLO 决定；超过预算可降低测量采样率，同时更新测量版本，保持补丁继续工作。

## 14. 最终报告的结论结构

不合并成一个没有范围的绿色状态。报告分别给出：

```text
installation_identity: MATCH / MISMATCH
symbolic_impact: COMPLETE_FOR_MODEL / PARTIAL / UNAVAILABLE
paired_function: PASS / FAIL / INSUFFICIENT
required_checkpoints: PASS / FAIL / INSUFFICIENT
live_distribution: STABLE / SHIFT / INSUFFICIENT
measurement_quality: VALID / DEGRADED
```

这些是证据状态，补丁执行动作仍是 PASS/BLOCK。

报告首页呈现受影响接口、已有证据、已确认功能回归、统计变化及尚未覆盖的正常分区。每个结论关联版本哈希、具体用例或统计窗口；符号模型、真实运行和线上统计可以独立复核。
